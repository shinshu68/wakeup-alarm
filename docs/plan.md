# wakeup-alarm 開発方針

## 目的・背景

Android 標準の時計アプリでは、寝坊対策の「予備のアラーム」を複数セットしておいても、問題なく起きられた日にそれらを一括でその日だけオフにする手段がない。毎回1つずつオフにするか、鳴らせたままにするしかない。

このアプリでは、本命アラームと予備アラームをまとめて登録し、起きられたときに「起きた」ボタン1つでその日の予備をまとめてオフにできるようにする。

利用者は開発者本人のみ（自分用）。

## スコープ

### やること

- **アラームグループ**：「本命1つ＋予備いくつか」を1つのグループとして登録・編集・削除・有効/無効の切り替えができる
- **「起きた」ボタンによる当日の予備一括オフ**
  - 「起きた」は、ロックを解除してアプリを開いた画面（一覧画面）からのみ押せる。寝ぼけた状態での誤操作を防ぐため、鳴動画面・通知には置かない
  - 押すと、そのグループの当日の残りの予備アラームを鳴らさない
  - 翌日以降の予備は通常どおり鳴る
- **鳴動時の表示と停止**
  - ロック中・消灯中：全画面の鳴動画面を表示し、「停止」で鳴動を止める
  - 端末を使用中：通知を表示し、通知の「停止」ボタンで鳴動を止める
  - 「停止」は鳴動を止めるだけで、予備は残す
- **曜日ごとの繰り返し**
- **着信音の選択**
- **バイブの設定**
- 端末の再起動後もアラームが鳴るようにする
- 必要な権限が許可されているかを確認し、未許可なら設定画面へ案内する

### やらないこと

- iOS 対応
- Google Play での公開（APK を端末に直接インストールして使う）
- 鳴動画面・通知からの「起きた」操作
- スヌーズ（今後の候補）
- ホーム画面のウィジェットからの「起きた」操作（今後の候補。アプリを開く手間が気になったら検討する）
- アカウント・クラウド同期

## 技術選定

| 項目 | 選定 | 理由 |
|---|---|---|
| UI・アプリ本体 | Flutter (Dart) | 開発者の希望 |
| アラームの登録・鳴動・通知 | `alarm` パッケージ | 鳴動・通知・全画面表示・再起動後の再登録をまとめて扱え、Kotlin を書かずに済む。通知のボタンは停止とスヌーズのみだが、「起きた」はアプリ画面からのみ押す方針なので支障がない |
| データ保存 | drift（SQLite） | 「グループ」と「その中のアラーム」の親子関係を素直に表せる。型安全で、マイグレーションも管理しやすい |
| 状態管理 | Riverpod | グループ一覧・編集・鳴動後の状態反映など、画面をまたぐ状態があるため |

当初は鳴動部分を Kotlin で自作し、通知に「起きた」ボタンを置く案だったが、ホーム画面から押せると誤操作のおそれがあるため、「起きた」をアプリ画面に限定し、`alarm` パッケージを使う方針に変更した。

## 設計方針

以下は計画時点の案。実装を進める中で見直す。

### データモデル（案）

- **AlarmGroup**：グループ名、有効/無効、繰り返す曜日、着信音、バイブの有無
- **AlarmItem**：所属グループ、時刻、本命か予備か、有効/無効
- **SkipRecord**：どのグループのどの日付の予備をオフにしたか（「起きた」を押した記録）

繰り返し・着信音・バイブはグループ単位で設定する想定。

### アラームの登録（案）

`alarm` パッケージのアラームは「日時を指定した1回きりのアラーム」なので、曜日の繰り返しはアプリ側で個々の鳴動日時に展開して登録する。

- 各アラームについて、数日先までの鳴動日時をまとめて `alarm` パッケージに登録する。通知から止めただけでアプリを開かない日が続いても、次回分が登録されていない状態を避けるため
- アプリの起動時・データの編集後・鳴動の通知を受けたときに、DB の内容と登録済みのアラームを突き合わせて登録し直す（再同期）
- 再同期の際、SkipRecord がある日付の予備は登録しない

### 処理の流れ（案）

1. グループを編集・保存 → drift で DB に書き込み → 再同期で `alarm` パッケージに登録
2. 時刻になる → `alarm` パッケージが鳴動・通知・全画面表示（アプリが終了していても鳴る）
3. 「停止」（鳴動画面または通知）：鳴動を止めるだけ。予備はそのまま
4. ロックを解除してアプリを開く → 一覧画面の該当グループで「起きた」を押す → SkipRecord を書き込み、当日の残りの予備の登録を取り消す

### 必要な権限（案）

`alarm` パッケージが必要な権限の多くを宣言するが、実行時の許可や設定画面での許可はアプリ側で確認する。

- 通知の表示（Android 13 以降は実行時に許可が必要）
- 時刻ちょうどに鳴らす（正確なアラーム）
- ロック中の全画面表示（Android 14 以降はユーザーの許可が必要な場合がある）

あわせて、メーカー独自の電池最適化でアラームが止められないよう、電池最適化の除外を案内する。

### ディレクトリ構成（案）

```
lib/
├── main.dart
├── app/          # ルーティング・テーマ
├── features/     # 画面ごとの UI と Provider（一覧・編集・鳴動・権限確認）
├── data/         # drift の DB 定義、リポジトリ
├── domain/       # モデル、鳴動日時の展開・スキップ判定
└── services/     # alarm パッケージとの連携（登録・再同期）
test/
```

## 進め方

マイルストーンの案。アラームが確実に鳴ることを先に実機で確かめる。

1. **環境構築**：Flutter プロジェクトの作成、Riverpod・drift・`alarm` パッケージの導入、lint の設定
2. **最小の鳴動**：固定時刻のアラーム1つを `alarm` パッケージで登録し、実機で「消灯中」「ロック中」「アプリ終了後」「再起動後」に鳴ること、鳴動画面と通知から停止できることを確認する
3. **グループの登録画面とデータ保存**：drift でのデータ保存、一覧・編集画面
4. **アラームの登録と曜日の繰り返し**：鳴動日時の展開、数日先までの登録、再同期
5. **「起きた」による当日の予備一括オフ**：一覧画面から
6. **着信音の選択とバイブの設定**
7. **権限の確認画面・電池最適化の案内と、実機での数日間の運用テスト**

## 未決事項

- 対象とする Android の最小バージョン（minSdk）。手元の端末の Android バージョンを確認して決める
- Android のアプリケーション ID（パッケージ名）
- 何日先までアラームを登録しておくか
- 「起きた」を押せる期間（本命の時刻より前、例えば鳴る前に目が覚めたときにも押せるようにするか。その場合に本命もオフにするか）
- 一覧画面での「起きた」の見せ方（当日まだ予備が残っているグループだけボタンを出す、など）
- 繰り返しなしのグループが鳴った後の扱い（自動で無効にするか）
- 「その日」の区切り（日付をまたぐグループ、例：23:50 本命・0:10 予備をどう扱うか）
- 鳴動を自動で止めるまでの時間（鳴りっぱなしにするか）
- 通知をスワイプしたときに鳴動を止めるか（`alarm` パッケージは Android 13 以降、既定でスワイプにより停止する）
- 着信音の選択方法。`alarm` パッケージに渡せる音源の形式（アプリ同梱の音源・端末内のファイル）を確認し、端末の着信音一覧から選べるかを検証して決める
- 鳴動画面を `alarm` パッケージ既定の動き（アプリの画面を開く）で作るか、専用の Activity を用意するか
- テスト方針（鳴動日時の展開・スキップ判定の単体テストの範囲）
