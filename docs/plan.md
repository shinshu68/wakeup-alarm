# wakeup-alarm 開発方針

## 目的・背景

Android 標準の時計アプリでは、寝坊対策の「予備のアラーム」を複数セットしておいても、問題なく起きられた日にそれらを一括でその日だけオフにする手段がない。毎回1つずつオフにするか、鳴らせたままにするしかない。

このアプリでは、本命アラームと予備アラームをまとめて登録し、起きられたときに「起きた」ボタン1つでその日の予備をまとめてオフにできるようにする。あわせて、家の Echo Dot に「アレクサ、おはよう」と話しかけるだけで、対象のグループの当日のアラームをオフにできるようにする。

利用者は開発者本人のみ (自分用)。使う端末は Pixel 6a と、家の Echo Dot。

## スコープ

### やること

- **アラームグループ**：「本命1つ＋予備いくつか」を1つのグループとして登録・編集・削除・有効/無効の切り替えができる
- **「起きた」ボタンによる当日の予備一括オフ**
  - 「起きた」は、ロックを解除してアプリを開いた画面 (一覧画面) からのみ押せる
  - 押すと、そのグループの当日の残りの予備アラームを鳴らさない
  - 翌日以降の予備は通常どおり鳴る
- **Alexa 連携**：「アレクサ、おはよう」で、対象のグループの当日まだ鳴っていないアラームをオフにし、結果を Alexa が読み上げる。詳細は [alexa-integration.md](alexa-integration.md)
- **鳴動時の表示と停止**
  - ロック中・消灯中：全画面の鳴動画面を表示し、「停止」で鳴動を止める
  - 端末を使用中：通知を表示し、通知の「停止」ボタンで鳴動を止める
  - 「停止」は鳴動を止めるだけで、予備は残す
- **曜日ごとの繰り返し**
- **着信音の選択**
- **バイブの設定**
- **ダークモード**：アプリ内で「端末の設定に従う／ライト／ダーク」を切り替えられる
- 端末の再起動後もアラームが鳴るようにする
- 必要な権限が許可されているかを確認し、未許可なら設定画面へ案内する

### やらないこと

- iOS 対応
- Google Play での公開 (APK を端末に直接インストールして使う)
- Alexa スキルの認定・公開 (開発ステージのまま自分のアカウントだけで使う)
- 鳴動画面・通知・ロック画面からの「起きた」操作
- Alexa からの鳴動の停止 (Alexa 連携は未来のアラームを当日分だけオフにする機能に限る)
- スヌーズ (今後の候補)
- ホーム画面のウィジェットからの「起きた」操作 (今後の候補。アプリを開く手間が気になったら検討する)
- アカウント・クラウド同期 (Firebase は Alexa 連携の受け渡しにだけ使う)

## 技術選定

| 項目 | 選定 |
|---|---|
| リポジトリ構成 | モノレポ (`app/` と `alexa-skill/`) |
| UI・アプリ本体 | Flutter (Dart) |
| アラームの登録・鳴動・通知 | `alarm` パッケージ |
| データ保存 | drift (SQLite) |
| 状態管理 | Riverpod |
| Alexa スキル | Alexa-hosted スキル (Node.js) |
| スキルとアプリの連携 | Firebase (FCM・Firestore・匿名認証、Spark プラン) |

### リポジトリ構成：モノレポ

アプリ (`app/`) と Alexa スキル (`alexa-skill/`) を1つのリポジトリに置く。FCM のデータのキーや Firestore のフィールド名など、両方でそろえる名前を同じリポジトリ・同じコミットで変えられ、1つのセッションで両側を見ながら直せるため。

- スキルを別のリポジトリにする方法は、そろえる名前がリポジトリをまたぎ、片方だけ変えて動かなくなる事故が起きやすいため採用していない

### UI・アプリ本体：Flutter

開発者の希望による。

### アラームの登録・鳴動・通知：`alarm` パッケージ

鳴動・通知・全画面表示・再起動後の再登録をまとめて扱え、Kotlin を書かずに済む。通知のボタンは停止とスヌーズのみだが、「起きた」はアプリ画面からのみ押す方針なので支障がない。

- 鳴動部分を Kotlin で自作し、MethodChannel で Flutter とつなぐ方法は、採用していない。通知に「起きた」ボタンを置くための案だったが、ホーム画面から押せると誤操作のおそれがあるため「起きた」をアプリ画面に限定し、自作する理由がなくなったため
- `android_alarm_manager_plus` と `flutter_local_notifications` を組み合わせる方法は、鳴り続ける音をバックグラウンドで扱うのが難しく、パッケージ同士のつなぎ込みで詰まりやすいため採用していない

### データ保存：drift

「グループ」と「その中のアラーム」の親子関係を素直に表せる。型安全で、マイグレーションも管理しやすい。

- shared_preferences に JSON で保存する方法は、データが増えたり構造を変えたりすると扱いにくいため採用していない

### 状態管理：Riverpod

グループ一覧・編集・鳴動後の状態反映など、画面をまたぐ状態があるため。

- Provider は、規模が大きくなると整理しにくいため採用していない
- setState のみで作る方法は、画面をまたぐ状態の共有が面倒になるため採用していない

### Alexa スキル：Alexa-hosted スキル (Node.js)

Alexa-hosted スキルは無料で、サーバーを自分で用意せずに済む。言語は、Alexa のサンプルや情報が多く、Firebase Admin SDK の機能もそろっている Node.js にする。

- Python は、Alexa のサンプルが Node.js より少なく、詰まったときに調べにくいため採用していない

### スキルとアプリの連携：Firebase

スキルからアプリへの呼び出しに FCM、結果の受け渡しに Firestore、書き込みの制限に匿名認証を使う。すべて無料の Spark プランで使い、請求先アカウントは紐づけない。構成と選ばなかった案は [alexa-integration.md](alexa-integration.md) に書く。

### 配布：自分用 (APK を直接インストール)

- Google Play で公開する方法は、アラーム用権限の申告・審査やストア掲載の準備が必要で、自分用には不要なため採用していない

## 設計方針

以下は計画時点の案。実装を進める中で見直す。

方式を決めたときは、その判断を書いた項目のすぐ下に、選ばなかった案と理由を書く。不具合の修正で選んだ方式も、あとから同じ形で追記していく。Alexa 連携に関わる判断は [alexa-integration.md](alexa-integration.md) の該当項目の下に書く。

### 予備アラームの持たせ方：グループ方式

「本命1つ＋予備いくつか」を1つのグループとして登録する。どれがどの本命の予備かが明確で、一括オフの対象が迷いなく決まるため。

- 本命の時刻と「◯分おきに◯回」を指定して予備を自動で作る方法は、予備を不規則な時刻にできないため採用していない
- 全部を独立したアラームにして予備に印を付ける方法は、本命が複数あるときにどの予備を消すかが曖昧になるため採用していない

### 予備を一括オフにする操作：アプリ画面の「起きた」ボタン

鳴動を止める「停止」と、当日の予備をオフにする「起きた」を分け、「起きた」はロック解除後のアプリ画面 (一覧画面) からのみ押せるようにする。寝ぼけた状態での誤操作を防ぐため。

- 本命を止めたら自動で予備もオフにする方法は、止めて二度寝すると予備が鳴らず、予備の意味がなくなるため採用していない
- 本命の停止後に「起きていますか？」の確認通知を出す方法は、操作も実装も増えるため採用していない
- 「起きた」を鳴動画面や通知に置く方法は、ロック解除なしで押せてしまい誤操作のおそれがあるため採用していない

### データモデル (案)

- **AlarmGroup**：グループ名、有効/無効、繰り返す曜日、着信音、バイブの有無
- **AlarmItem**：所属グループ、時刻、本命か予備か、有効/無効
- **SkipRecord**：どのグループのどの日付をオフにしたか、オフの範囲 (予備のみ：「起きた」／未鳴動の全アラーム：Alexa)

繰り返し・着信音・バイブはグループ単位で設定する想定。

### アラームの登録 (案)

`alarm` パッケージのアラームは「日時を指定した1回きりのアラーム」なので、曜日の繰り返しはアプリ側で個々の鳴動日時に展開して登録する。

- 各アラームについて、数日先までの鳴動日時をまとめて `alarm` パッケージに登録する
  - 鳴ったあとに次回分だけを登録する方法は、通知から止めただけでアプリを開かない日が続くと次回分が登録されない恐れがあるため採用していない
- アプリの起動時・データの編集後・鳴動の通知を受けたとき・Alexa からのオフを受けたときに、DB の内容と登録済みのアラームを突き合わせて登録し直す (再同期)
- 再同期の際、SkipRecord がある日付は、その範囲のアラームを登録しない

### 処理の流れ (案)

1. グループを編集・保存 → drift で DB に書き込み → 再同期で `alarm` パッケージに登録
2. 時刻になる → `alarm` パッケージが鳴動・通知・全画面表示 (アプリが終了していても鳴る)
3. 「停止」(鳴動画面または通知)：鳴動を止めるだけ。予備はそのまま
4. ロックを解除してアプリを開く → 一覧画面の該当グループで「起きた」を押す → SkipRecord を書き込み、再同期で当日の残りの予備の登録を取り消す

Alexa からのオフの流れは [alexa-integration.md](alexa-integration.md) の「構成」を参照する。

### 必要な権限 (案)

`alarm` パッケージが必要な権限の多くを宣言するが、実行時の許可や設定画面での許可はアプリ側で確認する。

- 通知の表示 (Android 13 以降は実行時に許可が必要)
- 時刻ちょうどに鳴らす (正確なアラーム)
- ロック中の全画面表示 (Android 14 以降はユーザーの許可が必要な場合がある)

あわせて、メーカー独自の電池最適化でアラームが止められないよう、電池最適化の除外を案内する。

## 未決事項

各マイルストーンの着手前に決めるものは、roadmap.md の該当マイルストーンにも記載している。

### アプリ

- 対象とする Android の最小バージョン (minSdk)。Pixel 6a の Android バージョンを確認して決める
- Android のアプリケーション ID (パッケージ名)
- 過去の時刻を指定してアラームを登録したときの扱い (翌日に鳴らすか、登録できないようにするか)
- 1つのグループに登録できる予備の数の上限と、本命より前の時刻の予備を許すか
- 2つのアラームの鳴動が重なったときの扱い (`alarm` パッケージの `allowAlarmOverlap` の設定)
- 「起きた」を押せる期間 (本命の時刻より前、例えば鳴る前に目が覚めたときにも押せるようにするか。その場合に本命もオフにするか)
- 一覧画面での「起きた」の見せ方 (当日まだ予備が残っているグループだけボタンを出す、など)
- 「その日」の区切り (日付をまたぐグループ、例：23:50 本命・0:10 予備をどう扱うか)
- 何日先までアラームを登録しておくか
- 繰り返しなしのグループが鳴った後の扱い (自動で無効にするか)
- 着信音の選択方法。`alarm` パッケージに渡せる音源の形式 (アプリ同梱の音源・端末内のファイル) を確認し、端末の着信音一覧から選べるかを検証して決める
- テーマ設定などアプリ全体の設定の保存先 (drift に入れるか、shared_preferences を使うか)
- カラーテーマ (色・モチーフ)
- 鳴動を自動で止めるまでの時間 (鳴りっぱなしにするか)
- 通知をスワイプしたときに鳴動を止めるか (`alarm` パッケージは Android 13 以降、既定でスワイプにより停止する)
- 鳴動画面を `alarm` パッケージ既定の動き (アプリの画面を開く) で作るか、専用の Activity を用意するか

### Alexa 連携

- `alexa-skill/` の中の構成と、モノレポから Alexa-hosted スキルへデプロイする手順 (git subtree など)
- 対象グループの指定方法 (アプリのグループに印を付けるか、スキル側でグループを指定するか)
- アプリとスキルの取り決めの具体的な名前と値 (alexa-integration.md の「アプリとスキルの取り決め」)
- Firebase の設定ファイル (`google-services.json` など) と、スキル側の環境変数の値の管理方法
- Alexa からのオフを、アプリの一覧画面でどう見せるか (オフにした日・件数の表示など)
